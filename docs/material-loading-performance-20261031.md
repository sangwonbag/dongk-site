# 자재 목록·상세 로딩 개선 검증 (2026-10-31)

기준 main: a9ae27bb786a2fb0bc922cb35dd72e03d8489114. 운영 배포/2초 목표 달성은 미확인.

## 확인한 원인과 구현

- AbortSignal이 있는 실제 페이지 호출에서는 요청 중복 제거가 작동하지 않았다. 목록·상세·검색에 공유 요청 풀을 적용하고 구독자 취소를 분리했다. 전체 요청 상한은 12초이며 종료 시 타이머/리스너를 정리한다.
- 목록의 단일 2000개 범위 요청과 검색의 limit(100)은 결과 누락 위험이 있었다. 실제 수신 건수/count 기반 페이지 조회와 안정적인 정렬을 적용했다. UI 30개씩 보기/검색 엔진/라인업 필터는 보존한다.
- 4초 후 미완료 서버 요청을 남기고 로컬 목록을 성공처럼 반환하던 처리를 제거했다. 서버 목록·검색 실패는 오류와 재시도로 연결하고 유효한 빈 응답은 보존한다. 서버 미설정 개발 환경에서는 기존 로컬 자료를 사용한다.
- 목록 5분/상세 10분 TTL을 적용하고 상세의 매번 강제 재조회는 사용자 재시도로 제한했다.
- 로컬 상품에 서버 행 변환 함수를 적용하던 오류를 수정했다. 서버 행 보완 시 반복 선형 탐색은 Map 조회로 바꿨다.
- 이미지 해시 JSON이 초기 매니페스트와 같은 번들에 포함되어 있었다. 별도 동적 청크로 분리했다. 상품/이미지 원본/화질/이미지 순서 규칙은 변경하지 않았다.
- 이미지 후보 배열의 참조 변경만으로 fallback이 재시작되지 않도록 URL 내용으로 비교한다. 상세 이미지 조회는 allSettled 병렬 처리한다. 대표 eager/high, 하단 lazy는 기존 정책을 유지한다.
- 상세 상품 이동 시 이전 상품/이미지 상태를 초기화하고 목록은 취소·언마운트 뒤 상태를 갱신하지 않는다.
- 목록/상세 필드는 이미 분리되어 있었다. description은 디아망 등 라인업 추론과 검색에 필요하므로 보존했다. DB 데이터·스키마·인덱스는 변경하지 않았다.

## 배포와 남은 작업

수정 전 운영에서 지정 URL의 로딩 화면과 이후 KCC 트랜디 450각 21개 표시를 확인했다. 신규 변경 검증은 아니다. Vercel 연결 계정의 프로젝트/팀 조회는 빈 목록이었다. 기존 main의 GitHub Vercel 상태는 success였다. 신규 상태는 PR에서 별도 확인하며 main 병합/운영 배포는 하지 않았다.

Preview에서 실제 DB의 6202→에코차음/디아망, 브랜드·두께·정렬·30개 표시, 빠른 필터 변경, 이미지 4종, 직접 진입·뒤로가기, 모바일 검증이 필요하다. 실제 네트워크 trace/DB 실행계획 없이 인덱스를 추정 생성하지 않았다. 전체 후보를 가져오는 대규모 검색의 첫 표시 지연도 추가 측정 대상이다.
